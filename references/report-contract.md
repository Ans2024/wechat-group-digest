# report.json 与写作约定

引擎 `wechat_local.report.validate` 检查来源存在、摘录逐字匹配、统计一致和完整阅读清单。它不判断结论是否被语义支持；作者必须阅读上下文核对。

```json
{
  "author": "当前 Codex 会话，完整阅读本次导出后撰写",
  "reviewed_message_ids": ["导出中的真实消息ID"],
  "overview": [{
    "text": "简短概览，保留主要话题与状态。",
    "message_ids": ["导出中的真实消息ID"],
    "evidence": [{"message_id": "导出中的真实消息ID", "quote": "该条消息的原文摘录"}]
  }],
  "topics": [],
  "todos": [],
  "confirmed": [],
  "unresolved": [],
  "other": []
}
```

六个栏目都必须是数组，没有合适内容时使用空数组，不编造事项来凑齐。各条目采用概览相同的 `text`、`message_ids`、`evidence` 结构。除概览外推荐增加简短 `title`，如“测试进展：导出功能已通过”。标题也必须受来源支持。

待办条目额外包含 `owner`、`deadline`、`status`；未明确的负责人或时间要求写“未明确”。每个引用 ID 至少提供一段对应来源的原文；`quote` 应是消息 `text` 或已解析 `reference` 中可核对的原文子串，不用改写后的概括代替摘录。

中文写作准则：

- 区分建议/决定、收到/同意、同意/完成；表情回应不能自动视为同意。
- 用“某成员表示”“卡片标题为”等标注信息层级，不将群内转述写成经过独立核实的事实。
- 当前窗口缺少前文时写明上下文不足，不向窗口外臆测。
- 内容较少时保持简洁，不把一件小事反复拆成很多结论。已确认事项写明确状态，不把“没有提出反对”写成一致通过。
- 用具有信息量的短标题和自然段呈现，省去无助于读者的实现说明。
- 页尾只保留时间范围、统计、同步/媒体识别边界。账号、群 ID、数据库路径等只用于本地核对，不进入分享正文或标题。

来源显示编号由渲染器按 `messages.json` 中消息顺序生成，从 1 开始。不要把该显示序号写入 `message_ids`；该字段必须仍是导出消息实际 ID。

零消息时，完整阅读清单为 `[]`，六个栏目也可为空；报告显示“本窗口无可用消息”，不能宣称没有发生任何讨论。

首次安装本技能的已验证环境：Windows build 26200 / Python 3.13.7 / 微信 4.1.13.65，读取、总结及新版渲染已在此前用户指定群完成。历史验证只作参考，每次任务仍应以本次命令返回为准。
